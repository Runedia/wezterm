# `umask` 크레이트 기능 명세

## 1. 개요 및 책임

`umask` 크레이트는 파일 생성 시 적용되는 권한 마스크(umask)를 일시적으로 제한했다가 복원하는 RAII 가드를 제공할 목적으로 설계된 워크스페이스 내부 크레이트입니다.

원본(upstream) 의도는 다음과 같습니다. 일부 Unix 사용자는 과도하게 관대한 umask(예: `000`, `002`) 환경에서 wezterm을 실행할 수 있으며, 이 상태에서 프로그램이 파일·디렉터리를 생성하면 의도보다 넓은 권한이 부여될 위험이 있습니다. 이를 막기 위해, 파일시스템에 무언가를 생성할 가능성이 있는 구간 동안에는 더 엄격한 umask를 설치하고, 해당 구간이 끝나면 이전 umask로 되돌립니다.

그러나 본 fork는 **Windows 전용 영구 분기**이며 플랫폼 코드가 이미 제거된 상태입니다. Windows에는 POSIX `umask` 개념 자체가 존재하지 않으므로, 현재 이 크레이트의 실제 책임은 **API 표면(타입과 RAII 수명 계약)만 유지하는 무동작(no-op) 호환 스텁**으로 축소되어 있습니다. 즉, 호출 측 코드가 변경 없이 컴파일·실행되도록 인터페이스를 보존하는 것이 유일한 실질적 책임입니다.

요약하면 다음과 같습니다.

- **명목상 책임**: 임계 구간 동안 umask를 제한하고 종료 시 복원하는 RAII 가드 제공.
- **현재 실질 책임(Windows fork)**: 동일한 공개 타입을 무동작으로 제공하여 호출부 호환성 유지.

## 2. 공개 API

크레이트는 단일 공개 타입 `UmaskSaver`를 노출합니다.

| 항목 | 시그니처 | 설명 |
| --- | --- | --- |
| `struct UmaskSaver` | `pub struct UmaskSaver {}` | 필드 없는 단위 형태(unit-like)의 가드 타입. |
| `UmaskSaver::new` | `pub fn new() -> Self` | 가드를 생성합니다. 원본 의도상 이 시점에 umask를 제한했어야 하나, 현재 구현은 빈 인스턴스만 생성합니다. |
| `impl Default for UmaskSaver` | `fn default() -> Self` | `Self::new()`로 위임합니다. `UmaskSaver::default()`로도 동일하게 생성할 수 있습니다. |
| `impl Drop for UmaskSaver` | `fn drop(&mut self)` | 가드가 스코프를 벗어날 때 호출됩니다. 원본 의도상 이전 umask를 복원했어야 하나, 현재 구현은 빈 본문입니다. |

### 사용 예시

```rust
use umask::UmaskSaver;

{
    let _saver = UmaskSaver::new();
    // 이 스코프 안에서 파일/디렉터리를 생성한다.
    // (원본 의도: 이 구간 동안 엄격한 umask 적용)
} // _saver가 drop되며 (원본 의도: 이전 umask 복원)
```

RAII 사용 규약상 반환된 가드는 반드시 변수에 바인딩하여 임계 구간 끝까지 살아 있게 해야 합니다. `let _ = UmaskSaver::new();`처럼 즉시 폐기하면 가드가 그 자리에서 drop되어 의미가 사라집니다(현재 구현에서는 어차피 무동작이지만, 향후 동작이 복원될 경우를 대비해 규약을 지키는 것이 안전합니다).

## 3. 내부 구조

전체 구현은 `src/lib.rs` 한 파일, 약 24행으로 구성되며 다음 네 부분으로 나뉩니다.

1. **타입 정의** — `pub struct UmaskSaver {}`. 상태를 보존할 필드가 없습니다. 원본이라면 복원에 사용할 이전 umask 값(예: `mode_t`)을 필드로 보관했겠으나, 무동작 스텁이므로 비어 있습니다.
2. **`Default` 구현** — `default()`가 `new()`를 호출합니다. 이는 Clippy의 `new_without_default` 권고를 충족하기 위한 관용적 패턴입니다(인자 없는 `new`가 있으면 `Default`도 제공).
3. **생성자 `new`** — 빈 구조체를 반환합니다. 부작용이 없습니다.
4. **`Drop` 구현** — 본문이 비어 있습니다. 복원 로직이 제거되었습니다.

상태가 전혀 없으므로 본 타입은 `Send`/`Sync` 자동 구현 대상이며, 복사·이동 제약도 없습니다(단, `Drop`을 구현하므로 `Copy`는 불가합니다).

## 4. 의존 관계

- **외부 크레이트 의존성**: 없습니다. `Cargo.toml`의 `[dependencies]` 섹션이 비어 있습니다.
- **표준 라이브러리 사용**: `core`/`std`의 트레이트(`Default`, `Drop`)만 사용하며 OS API 호출은 없습니다.
- **빌드 메타데이터**: `edition = "2018"`, `version = "0.1.0"`, `publish = false`. `publish = false`는 crates.io 게시를 차단하는 워크스페이스 내부 전용 크레이트임을 의미합니다.
- **역의존(이 크레이트를 쓰는 쪽)**: wezterm 워크스페이스의 다른 크레이트들이 시작 초기화나 파일 생성 임계 구간에서 `UmaskSaver`를 사용하도록 설계되어 있습니다. 호출부가 본 크레이트에 의존하므로, API 시그니처는 호환성을 위해 보존되어야 합니다.

## 5. 핵심 타입 및 동작

### `UmaskSaver`

- **개념**: RAII 가드. 생성 시점에 부작용(umask 제한)을 일으키고, drop 시점에 그 부작용을 되돌리는 것이 원래의 동작 모델입니다.
- **수명 계약**: 가드의 수명(lifetime)이 곧 "엄격한 umask가 적용되는 구간"입니다. 생성과 drop 사이에서 파일시스템 생성 작업이 일어나야 의미가 있습니다.
- **현재 동작**: `new`와 `drop` 모두 무동작입니다. 따라서 어떤 umask 상태도 변경·복원되지 않으며, 어떤 시스템 콜도 발생하지 않습니다. 가드는 순수하게 컴파일·호출 호환성을 위한 자리표시자입니다.
- **실패 모드**: 없습니다. 생성·소멸 모두 패닉을 일으키지 않으며 반환 타입도 `Result`가 아닙니다.

## 6. Windows 전용 고려사항

- **POSIX `umask` 부재**: Windows의 보안 모델은 ACL(Access Control List)/DACL 기반이며, Unix식 프로세스 단위 권한 마스크(`umask(2)`)에 해당하는 개념이 없습니다. 따라서 이 크레이트의 원래 핵심 기능은 Windows에서 의미를 가질 수 없으며, 무동작 스텁으로 둔 것은 플랫폼상 올바른 선택입니다.
- **플랫폼 코드 삭제 완료**: 본 fork 방침에 따라 `libc::umask` 호출 등 Unix 전용 구현은 이미 제거되었습니다. 남은 것은 플랫폼 중립적인 빈 껍데기입니다.
- **권한 통제 대안**: 만약 Windows에서 생성 파일의 권한을 실제로 통제해야 한다면, umask가 아니라 보안 디스크립터(SECURITY_DESCRIPTOR)/ACL을 명시적으로 설정하는 별도 메커니즘이 필요합니다. 그러한 요구는 이 크레이트의 범위 밖이며, 현재로서는 도입되어 있지 않습니다.
- **`cfg` 분기 부재**: 코드에 `#[cfg(unix)]` / `#[cfg(windows)]` 분기가 남아 있지 않습니다. 단일 무조건(unconditional) 구현이므로 플랫폼별 컴파일 차이가 없습니다.

## 7. 리팩토링 주의점

- **공개 API 보존**: `UmaskSaver`, `UmaskSaver::new`, `Default`, `Drop`는 호출부와의 계약입니다. 시그니처 변경·제거 시 워크스페이스 내 사용처가 깨질 수 있으므로, 변경 전 역의존 검색(예: 워크스페이스 전체에서 `UmaskSaver` 참조 grep)이 필요합니다.
- **무동작 제거의 유혹**: 동작이 없다고 해서 크레이트 전체를 삭제하고 호출부를 정리하는 방식은 가능하지만, 그 경우 다수의 호출 지점을 동시에 수정해야 하며 RAII 패턴이 주는 "구간 표시" 가독성을 잃습니다. 인터페이스 유지를 택했다면 빈 구현을 그대로 두는 편이 변경 범위를 최소화합니다.
- **`Default` ↔ `new` 동기화**: `default()`가 `new()`에 위임하므로, `new`에 인자나 부작용을 추가할 경우 `Default` 구현의 적절성을 재검토해야 합니다(인자 없는 기본 생성이 더 이상 타당하지 않을 수 있음).
- **`Drop`에 로직 추가 시**: `Drop`에 실패 가능 동작(예: 시스템 콜)을 넣을 경우, drop은 오류를 전파할 수 없으므로 패닉·무시·로깅 중 정책을 명시해야 합니다. 또한 drop 중 패닉은 언와인딩 도중이면 프로세스 abort로 이어질 수 있으므로 주의가 필요합니다.
- **상태 필드 도입 시 자동 트레이트 영향**: 향후 OS 핸들 등 비-`Send`/비-`Sync` 필드를 추가하면 `UmaskSaver`의 자동 트레이트 구현이 사라져 멀티스레드 사용처에 영향을 줄 수 있습니다.
- **`edition = "2018"`**: 워크스페이스 일관성 차원에서 더 높은 에디션으로 통일할 여지가 있으나, 코드가 trait 구현뿐이라 에디션 차이로 인한 동작 변화는 없습니다.
